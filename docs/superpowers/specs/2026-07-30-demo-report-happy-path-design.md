# Atlas Ads 演示报告 Happy Path 设计

## 目标

先跑通一条完整且可信的页面流程：

```text
卖家填写基础资料
→ 系统计算总预算边界并冻结输入
→ 载入明确标记的固定 SP 演示数据
→ 生成页面表格报告
→ 用确定性模板解释搭建理由
→ 将报告写入本地运行快照
```

这条流程用于验证交互、报告结构和透明度，不代表已生成可执行的 Amazon 广告方案。

## 成功标准

卖家填写现有必填项后，只需点击一次“生成演示报告”，即可在页面看到：

1. 一张简单的广告搭建表；
2. 一段说明为什么采用这套结构的确定性总结；
3. 清晰的演示数据与资源使用声明；
4. 可回读的本地运行快照。

报告不得暗示已连接 Amazon、MCP 或真实类目数据，也不得把固定样例包装成卖家的真实策略。

## 第一版范围

### 包含

- 沿用现有卖家基础资料表单。
- 沿用确定性预算可行性计算。
- 固定生成三条 SP 演示 Campaign。
- 在页面内生成可读表格报告。
- 使用确定性模板生成自然语言总结。
- 保存完整报告到本地运行快照。
- 展示数据来源、模型调用次数和执行边界。

### 不包含

- Amazon Ads API 或 MCP 连接。
- 卖家表格导入。
- 真实关键词、ASIN 或类目基准查询。
- LLM 调用。
- 自动创建或修改广告活动。
- Excel、Markdown 或 PDF 导出。
- SB、SD 的正式预算和投放建议。

## 报告结构

报告主体只保留一张广告搭建表：

| 广告类型 | 广告目的 | 日预算 | 具体投放词 / ASIN | 投放类型 |
|---|---|---:|---|---|
| SP | 探索搜索词 | 按演示规则分配 | `demo running socks` | 自动采样 |
| SP | 验证核心词 | 按演示规则分配 | `demo compression socks` | 精准 |
| SP | 验证关联商品 | 按演示规则分配 | `DEMO-ASIN-001` | 商品投放 |

每一行代表一个 Campaign 草案。第一版不加入状态、证据、规则等额外列，以保持卖家阅读简单。追溯信息保留在报告顶部说明和运行快照中。

## 预算规则

总日预算来自现有可行性计算：

```text
月销售目标 × 产品售价 × 目标 TACoS ÷ 30
```

演示报告将总日预算按固定演示比例拆为三行：

- 自动采样：30%
- 精准验证：45%
- 商品投放：25%

三行金额之和必须等于总日预算；金额仅保留两位小数，最后一行吸收四舍五入差额。

这些比例属于 `demo-report-v1` 演示规则，不是 Amazon 最佳实践、类目基准或卖家真实建议。

## 确定性总结

总结不调用模型。它从固定规则与计算结果中填充一段自然语言：

> 本次演示将总日预算拆分为三种 SP 任务：自动采样用于收集搜索词信号，精准投放用于验证核心词，商品投放用于演示关联 ASIN 测试。预算分配来自固定演示规则，不代表真实市场建议。正式执行前仍需补充关键词、商品定向和账户资格证据。

若预算可行性存在冲突，总结需要额外指出当前输入假设之间存在冲突，但仍可展示演示表格用于体验流程；页面不得把它标记为“可执行”。

## 透明度声明

报告顶部固定展示：

- 报告类型：演示报告；
- 数据来源：卖家填写 + 固定演示数据；
- 外部数据：未使用；
- 模型调用：0 次；
- 执行状态：不可直接执行。

演示关键词、ASIN 和预算拆分必须有明显的“演示”标签。

## 交互流程

现有多个操作按钮会收束成清晰的主次关系：

1. “保存草稿”保留为次要操作；
2. “生成演示报告”作为唯一主操作；
3. 点击主操作后，系统依次完成输入校验、预算计算、运行创建和报告渲染；
4. 页面滚动或聚焦到报告区；
5. 报告生成失败时保留用户输入，并显示具体字段或本地服务错误。

可行性、Gate 和 Campaign 架构的详细调试入口暂时不删除，但从主流程中降级为“查看计算详情”，避免新用户必须逐个点击才能完成流程。

## 组件边界

### 演示报告生成器

输入：

- 已验证的 intake；
- 确定性 feasibility 结果。

输出：

- `report_version`；
- 演示标识与透明度元数据；
- 三条 SP 表格行；
- 确定性总结；
- 可行性状态与警告。

它不读取网络、不调用模型、不访问本地存储。

### 本地 API

新增单一报告端点，负责：

1. 验证输入；
2. 标准化卖家证据；
3. 计算可行性；
4. 生成演示报告；
5. 创建不可变运行快照；
6. 返回报告与运行 ID。

现有底层端点继续保留，供测试和后续高级模式使用。

### 页面报告区

页面只消费报告端点返回的数据，不在浏览器中重新计算预算或拼装业务规则。这样页面展示与本地快照使用同一份结果。

## 数据与快照

运行快照中的 `decision-plan.json` 新增 `demo_report`：

```json
{
  "report_version": 1,
  "report_type": "demo",
  "is_executable": false,
  "data_source": "seller_input_and_fixed_demo_data",
  "external_data_used": false,
  "model_calls": 0,
  "rows": [],
  "summary": "",
  "warnings": []
}
```

已有输入、可行性、Gate 和架构结果继续保存。历史快照不回写、不升级。

## 错误处理

- 输入无效：返回具体字段错误，不创建运行。
- 本地存储失败：返回存储错误，不显示虚假的成功报告。
- 可行性冲突：生成带警告的演示报告，但标记为不可执行。
- 演示规则内部金额不守恒：测试失败并阻止发布。
- 缺少会话 token：保持现有 401/403 安全边界。

## 测试策略

按测试驱动方式实现：

1. 生成器输出固定三行 SP 数据；
2. 三行预算之和等于总日预算；
3. 报告始终标记 `is_executable: false`；
4. 报告始终记录 `external_data_used: false` 和 `model_calls: 0`；
5. 可行性冲突会进入 warnings；
6. 报告 API 一次请求创建快照并返回相同报告；
7. 页面存在一个主操作、五列表格和确定性总结；
8. 现有 token、草稿、Gate 和快照测试继续通过。

## 后续替换点

未来接入 MCP 或卖家表格时，不改变页面表格结构。只替换报告生成器前的数据适配层：

```text
固定演示数据
→ 来源中立的 evidence_context
→ Gate
→ 真实报告生成器
```

真实报告必须继续满足现有 `decision-rules.yaml` 与 `output-schema.json`，并保留来源、采集时间、规则版本和人工确认边界。
